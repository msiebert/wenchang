Memory your agent files for itself.

A small filesystem of markdown files for your AI agent. The agent decides what to remember and where to file it. wenchang supplies the storage, versioned writes, scope rules, and the prompt.

For teams building chat assistants, coding agents, and analytics copilots that should remember users, projects, and organizations.

The memory index#

Every session starts with get_memory_index(). Each entry is a path, a version, and a description the agent matches against. These four come from the usage walkthroughs; pick one to follow it.

Instructions for AI agents#

wenchang/index.md#for-agentsfull text with exact names

  1. Check for Python 3.12 or newer and an MCP client that can launch a stdio server.
  2. Install from git: pip install "wenchang[mcp] @ git+https://github.com/msiebert/wenchang". There is no PyPI release, CLI, or environment variable.
  3. Write server.py from the quickstart, ending in build_server(...) and server.run("stdio").
  4. Pick storage: InMemoryStorage for trials, GcsStorage(bucket) to persist.
  5. Ask the user which scopes exist, which are shared, and who may write each. See customize.
  6. Register the server with the MCP client, for example claude mcp add memory -- /path/to/python /path/to/server.py.
  7. Verify that exactly seven tools are listed.
  8. In use, call get_memory_index first, pass expected_version on every write, never write to system/, and never store account numbers, health diagnoses, or signs the user is a minor.

Machine-readable: llms.txt, llms-full.txt, and a Markdown twin of every page.

How it works#

The agent never sees storage. It sees seven tools and a prompt.

  1. The agent calls a tool such as append_line(scope, area, name, line, expected_version). It addresses a file by scope, area, and name.
  2. The tool layer (wenchang.tools, mounted on MCP by wenchang.mcp) resolves the caller's identity on every call, fills in the caller's own entity ID for the scope, refuses writes to system/ and to scopes the policy gates by role, and forwards the call to a TransportClient.
  3. MemoryStore (reached through InProcessClient today) enforces the per-file size limit, merges metadata, and makes every write conditional on the version the agent read.
  4. Storage is a small get/put/list protocol. GcsStorage implements it on one GCS bucket: markdown body as the object, metadata as custom object metadata, GCS generation as the version.

Files live at {scope}/{entity_id}/{area}/{name}.md. A scope is a visibility tier you define (the reference adopter uses user, project, and organization); the entity ID says whose copy of that scope it is.

See it work#

An illustrative exchange. Tool names, arguments, and result shapes are real; the agent's wording is representative, not recorded. The full tool-call detail is on the usage page.

Session 1

  • You: I prefer bar charts for my weekly reports.
  • Agent calls get_memory_index(). The index is empty.
  • Agent calls write_file(scope="user", area="preferences", name="charts", content="- [stated] Prefers bar charts for weekly reports.\n", description="Chart preferences for reports", aliases=["weekly report charts"], expected_version=null).
  • Agent: Got it. I'll remember bar charts for your weekly reports.

Session 2, days later, a brand-new conversation

  • You: Which chart type should I use for this week's report?
  • Agent calls get_memory_index(). One entry: user/u-ada/preferences/charts.md, "Chart preferences for reports".
  • Agent calls read_file(scope="user", area="preferences", name="charts") and reads - [stated] Prefers bar charts for weekly reports.
  • Agent: Use a bar chart. You told me you prefer them for your weekly reports.

Key properties#

  • no schemaAgent-organizedThe agent files each fact in the file about its subject and finds files by description and aliases. There is no content search.
  • versionedOptimistic concurrencyEvery write names the version it read. A stale version returns the current content, so the agent merges and retries.
  • scopedScope authorizationEach call resolves an Identity. A ScopePolicy says which roles may write which scope, and paths come from the caller's own grants.
  • read onlyCurated system/ areaPeople maintain it. The agent can read it and never change it. A correction goes in a normal area and wins.
  • prompt rulePrivacy in the promptThe agent is told to refuse account numbers, health diagnoses, and anything indicating a minor. It is guidance, not a content filter.
  • pluggableTransport-agnosticTools talk to a TransportClient. InProcessClient calls a MemoryStore directly; a remote transport is planned.
  • loggedObservableon_call receives a ToolCallRecord after every MCP tool call.
  • markdownPlain filesA markdown body with its metadata stored beside it, at {scope}/{entity_id}/{area}/{name}.md.

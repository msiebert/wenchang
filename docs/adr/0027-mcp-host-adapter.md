# 0027. MCP host adapter

Date: 2026-10-08

## Status

Accepted

## Context

Section 7 of the Notion spec says the library "ships as its own server
instance with the memory tools decorated onto it". A host picks the tool
names, schemas, and descriptions up "with no manual wiring", optionally
under a namespace prefix. ADR 0022 decision 12 deferred that server to
AIE-1060.

AIE-1060 adds an MCP (`MCPServer`) host adapter as an optional dependency,
with seven thin wrappers. The issue text calls it FastMCP. Each wrapper:

1. takes the session's credentials from the request context;
2. binds that session's `MemoryTools` with `bind_tools`;
3. forwards the call;
4. returns `render_result` or `render_error` output.

Two requirements were added later:

- **2026-10-07.** The assembled prompt is the server's `instructions` and is
  also an MCP resource.
- **2026-10-08.** The descriptions in `tools/list` come from a
  session-independent `tool_descriptions(product)`. Wrappers are registered
  with explicit names and descriptions, and startup fails if a description
  is missing, as happens under `python -OO`.

Facts about the framework, verified against `mcp` 2.2.0 and 2.3.0:

- **FastMCP was renamed.** The current official `mcp` package is 2.x, and
  FastMCP is now `MCPServer`.
- **The protocol is stateless.** It implements the 2026-07-28 protocol.
  `ctx.session` is a new object on every request, and there is no
  per-connection session id.
- **Sync tools run concurrently.** They run on worker threads, so parallel
  calls overlap on every transport.
- **Arguments are validated before the wrapper runs.**
- **Some strings are pre-parsed as JSON.** This applies to string arguments
  whose annotation is not exactly `str`.

## Decision

Add `src/wenchang/mcp.py`, installed with the `mcp` extra. It exports
`register_memory_tools`, `build_server`, `memory_instructions`,
`ToolCallRecord`, and `PROMPT_RESOURCE_URI`. Also add
`wenchang.tools.tool_descriptions`, and make `InMemoryStorage` thread-safe.

1. **Dependency: the official `mcp>=2.2,<3`, using `MCPServer`.** The
   requirement sits in the `mcp` extra and in the `dev` group. Importing
   `wenchang.mcp` without it raises an `ImportError` naming
   `wenchang[mcp]`. An installed `mcp` that lacks `mcp.server.mcpserver`
   raises a different `ImportError`, saying the installed `mcp` is
   incompatible with `mcp>=2.2,<3`. No other `wenchang` module imports
   `mcp`.
   - **Rejected: `mcp<2`, which still names the class `FastMCP`.** It is the
     legacy protocol line.
   - **Rejected: the standalone `fastmcp` package.** It is a third-party
     framework with a heavier dependency tree.
2. **`tool_descriptions(product=None)` is public in `wenchang.tools`.** It
   renders the text `MemoryTools.descriptions()` gave, and
   `MemoryTools.descriptions()` now delegates to it. The server registers
   tools before any session exists, so it needs a session-independent
   source. A tool whose docstring is `None` gets `""`, so the startup check
   in decision 8 can report it.
   - **Rejected: raising inside `tool_descriptions` when a docstring is
     missing.** Returning `""` keeps the function total, so
     `MemoryTools.descriptions()` never raises. The server's startup check
     owns the error, and it names every affected tool at once.
3. **Registration on the adopter's own server.**
   `register_memory_tools(server, *, prompt, client, resolver, policy,
   credentials_from_context, source, product=None, tool_prefix=None,
   on_call=None)` adds the seven tools and the prompt resource to an
   `MCPServer` that the adopter builds. The adopter keeps its own auth,
   middleware, lifespan, and other tools.
   - `build_server(*, slots, ..., name="wenchang")` is a convenience. It
     constructs `MCPServer(name, instructions=memory_instructions(slots))`
     and calls `register_memory_tools`.
   - This is the closest equivalent to Section 7's "mount". `MCPServer`
     has no mount or compose API.
4. **Explicit `name=` and `description=`, and wrappers without
   docstrings.** Each wrapper is registered with
   `add_tool(fn, name=..., description=tool_descriptions(product)[name])`.
   - Each wrapper's parameters mirror the `MemoryTools` method exactly:
     names, order, annotations, and defaults. A keyword-only
     `ctx: Context[Any, Any]` is added, which `MCPServer` injects and keeps
     out of the schema. The annotation must name `Context` directly,
     because `MCPServer` does not see through a type alias.
   - **Rejected: setting `__doc__` before registration.** It is
     unnecessary, since `mcp` 2.x takes `description=`.
   - **Rejected: wrappers generated by copying signatures.** Hand-written
     wrappers stay readable and type-checked, and a schema test catches
     drift.
5. **Bind per tool call.** Every call works the same way:
   1. Call `credentials_from_context(ctx)`. It returns the raw credential,
      for example a bearer token taken from `ctx.headers`.
   2. Call `bind_tools` with it. The resolver verifies the credential.
   3. Discard the `MemoryTools` after the call.

   Headers and `_meta` are client-supplied and are never treated as an
   identity assertion.
   - **Why per call.** Under the stateless 2026-07-28 protocol, this is the
     only reading of "the session's credentials". There is no session
     object or id that lasts across requests. In legacy handshake mode, a
     private per-connection object exists
     (`ctx.request_context.session._connection`), but it is absent under
     the modern protocol that clients negotiate by default.
   - **Hard requirement met.** A per-call binding can never share one
     identity across callers.
   - **What it supersedes.** This replaces ADR 0022 decision 2's "identity
     resolved once per session" at the MCP surface, and its rejection of
     "resolving lazily on first use".
   - **Mid-conversation failure.** "Identity could not be resolved; memory
     is unavailable for this session" can now surface mid-conversation,
     not only at session start. The agent's instruction is the same either
     way: continue without memory.
   - **Cost.** The resolver runs on every call. A resolver may cache
     internally, since it must already be consistent within a session (ADR
     0014).
   - **Extraction failures.** If `credentials_from_context` raises, the
     call renders a permanent
     `ResolverFailureError("Credentials could not be read from the request.")`.
     One `WARNING` is logged on `wenchang.mcp` with the tool name and the
     exception's type name only. The exception's message, arguments,
     traceback, and chain are never rendered or logged, because they may
     carry the credential.
   - **Rejected: a cache keyed by session id.** There is no stable id.
   - **Rejected: a cache keyed by credentials.** It would hold credentials
     in memory.
   - **Rejected: one shared binding.** Every caller would get one identity.
   - **Rejected: credentials as a tool argument.** The agent would control
     them.
6. **Results are `CallToolResult`.** Each result carries the rendered
   payload twice: as `structured_content`, and as its JSON in one text
   content. `is_error` is true when the payload came from `render_error`.
   An `internal`-category error is logged on logger `wenchang.mcp` at
   `ERROR` with `exc_info`, because `render_error` hides its message from
   the agent. Returning `CallToolResult` also publishes no output schema.
7. **Concurrency.** `MCPServer` runs the sync wrappers on worker threads, so
   the `TransportClient` is called concurrently and must be thread-safe.
   - `InProcessClient` and `MemoryStore` keep no mutable state of their own
     between calls. Their compare-and-swap rests on `Storage`.
   - `InMemoryStorage` now holds a lock across each method, so the fake
     matches GCS compare-and-swap and token uniqueness under concurrency
     (Constitution V, ADR 0003 note).
   - The thread-safety of the `google-cloud-storage` client object used by
     `GcsStorage` is not verified here.
8. **Startup checks.** `build_server` checks everything before it builds the
   prompt or a server. `register_memory_tools` checks everything before it
   registers anything.
   - **Argument types.** `client`, `policy`, `source`, and `product` reuse
     `MemoryTools`' exact errors. `resolver` must satisfy
     `IdentityResolver`, `credentials_from_context` must be callable, and
     `on_call` must be callable or `None`. Neither may be an `async`
     function, because the wrappers call them synchronously on worker
     threads. For `register_memory_tools`,
     `server` must be an `MCPServer`, and `prompt` must be a non-empty
     `str`.
   - **Prefix.** `tool_prefix` is `None`, or 1 to 64 characters of
     `[A-Za-z0-9_-]` starting and ending with a letter or digit. The
     registered name is `f"{tool_prefix}_{name}"`, which stays within
     MCP's tool-name character set and length limit.
   - **Descriptions.** Every description must be present and non-blank.
     Otherwise startup raises
     `RuntimeError("memory tool descriptions are missing or empty for: ...;
     the tool docstrings may have been stripped (python -OO)")`. This check
     is load-bearing, because `add_tool(description="")` silently falls
     back to the wrapper's docstring.
   - **Collisions.** None of the seven target names, and not
     `PROMPT_RESOURCE_URI`, may already be registered on the server. The
     `ValueError` lists every collision in one sorted, comma-separated join.
     `MCPServer` only logs a duplicate, which would silently keep one
     registration and drop the other. The check reads `mcp`'s private tool
     and resource managers, which the `<3` pin keeps stable.
9. **Prompt delivery.** `memory_instructions(slots)` returns
   `build_memory_prompt(slots)`. `build_server` calls it once and passes the
   result as `instructions`. Clients receive it as
   `InitializeResult.instructions` in the legacy handshake, or through
   discover in the modern protocol.
   - The same text is served as the resource `wenchang://memory-prompt`,
     with type `text/markdown`, for clients that drop `instructions`.
   - `MCPServer.instructions` is read-only after construction. So
     `register_memory_tools` takes the built `prompt`, and logs a warning
     when the server's instructions are `None` or do not contain it.
10. **The `on_call` observer.** After every wrapper call, `on_call` receives
    a `ToolCallRecord`, holding:
    - `tool`: the registered name;
    - `arguments`: the arguments the wrapper received;
    - `result`: a deep copy of the payload sent as `structured_content`;
    - `is_error`;
    - `request_id`: the MCP request's id. Under parallel calls, records
      arrive in completion order, so this is how a consumer correlates them;
    - `duration_s`: the wrapper's wall time on a monotonic clock.

    Records compare by value. They are unhashable, because `arguments` and
    `result` are mappings.

    It runs on the call's worker thread, possibly concurrently with other
    calls, and the response waits for it. It must therefore be thread-safe
    and fast. An exception from `on_call` is logged at `ERROR` and never
    reaches the client. AIE-1170's eval grader uses it as an MCP-layer
    trace.
    - **Rejected: MCP middleware.** It sees raw requests, not the rendered
      payload.
11. **Deviations at the MCP surface.** `MCPServer` validates arguments
    against the generated schema before the wrapper runs.
    - **Schema errors bypass the tool layer.** A wrong-type or missing
      argument returns `is_error=True` with pydantic's message, which names
      the argument. There is no `structured_content`, no category, and no
      `on_call` record. This precedes ADR 0022 decision 13's
      `InvalidArgumentError`, which still applies to everything the schema
      admits.
    - **JSON pre-parsing.** For a parameter not annotated exactly `str`,
      `mcp` first tries to parse a string argument as JSON.
      - `"null"` becomes `None`. So `list_prefix(area="null")` lists the
        whole scope, and `description="null"` on `append_line` or
        `replace_fact` means "no change".
      - `"[1]"` becomes a list and then fails validation.
      - Version tokens are digit strings and stay strings.

      This is documented and pinned by tests, not worked around, because
      working around it would mean fighting the framework's argument
      handling.
12. **Rejected: a minimal local gRPC client as the smoke-test driver.** The
    issue's first paragraph asks for one. Its 2026-10-08 requirements make
    a real MCP client the driver, and the smoke test asserts against
    `tools/list` exactly as a host sees it. A gRPC client would test
    nothing the MCP client does not, and the production gRPC transport is
    out of scope. This is a deviation from the issue text.

## Consequences

The library can be served to any MCP client, over stdio
(`server.run("stdio")`) or HTTP, or mounted as seven tools on an adopter's
own server. The core still has no server-framework dependency.

What the agent sees in `tools/list` is pinned by a smoke test that drives a
real `mcp` client:

- the names, with and without a prefix;
- the descriptions;
- the input-schema parameters, required sets, and types;
- the `instructions`;
- the prompt resource.

A change to a `MemoryTools` signature, or to `mcp`'s schema generation,
fails that test.

Concurrency is now part of the adopter contract: a `TransportClient` served
through `wenchang.mcp` must be thread-safe. `InMemoryStorage` is, and
`GcsStorage` is a follow-up.

The resolver runs on every tool call, which adds latency for a remote
resolver. The resolver failure message, which says memory is unavailable
"for this session", may appear mid-conversation.

Agent mistakes in argument types reach the agent as pydantic text rather
than as rendered `InvalidArgumentError` payloads. The two `"null"` cases
silently mean "omitted".

The collision check depends on private `mcp` attributes and must be
revisited when the `<3` bound is lifted.

`ToolAnnotations` (`readOnlyHint`, `destructiveHint`) are not set. That is
a follow-up.
